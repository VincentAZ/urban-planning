# Urban Planning API

The API implements free accounts, durable organization workspaces, optimistic project saves, scenario commands, source-bound calculations, PDF/Word/CSV/XLSX/GeoJSON exports, staged GeoJSON imports, comments, roles, immutable public snapshots, and opt-in public feedback. It listens on port 3001 behind the Vite `/api` development proxy.

Run `corepack pnpm dev:api` from the repository root using Node 22.13 or later. With no `DATABASE_URL`, development saves scoped records to `.local/api-state.json.sqlite` using SQLite transactions and restrictive file permissions. Existing JSON is migrated with full-state verification and preserved unchanged. Stop older writers before cutover; the JSON is not a current backup afterward. This adapter refuses production mode. See [storage, migration, and recovery](../../docs/STORAGE.md).

For a new local PostgreSQL/PostGIS schema, start `docker compose up -d database`, then provision separate application logins:

```bash
DATABASE_MIGRATION_URL=postgresql://urban:urban-local-development-only@127.0.0.1:54329/urban_planning corepack pnpm exec tsx scripts/db-provision.ts --schema urban_app --out .local/database-config
node --env-file=.local/database-config/operator.env --import tsx scripts/db-migrate.ts
node --env-file=.local/database-config/runtime.env --import tsx apps/api/src/index.ts
```

The password above is exclusively a local development default. Supply a private password in deployed infrastructure. If Docker Compose is unavailable, an equivalent isolated database can be started with:

```bash
docker run --name urban-planning-postgres --detach \
  --publish 127.0.0.1:54329:5432 \
  --env POSTGRES_DB=urban_planning --env POSTGRES_USER=urban \
  --env POSTGRES_PASSWORD=urban-local-development-only \
  --volume urban-planning-postgres:/var/lib/postgresql/data postgis/postgis:17-3.5
```

Provisioning refuses existing schemas, roles, and credential directories. It writes separate private `operator.env` and `runtime.env` files; keep the operator file out of application containers. This fresh-schema command does not migrate an existing schema into a new one. Existing installations must back up their current schema and provision restricted roles against that schema before migration. See [the migration and security contract](../../docs/STORAGE.md).

The server verifies restricted database roles at startup and never applies migrations. Migrations require `DATABASE_MIGRATION_URL`; web, authentication and worker connections use `DATABASE_URL`, `DATABASE_AUTH_URL`, and `DATABASE_WORKER_URL`. `/api/v1/health` reports the actual storage adapter and authentication capability. `/api/v1/capabilities` reports implemented services and unavailable national/AI/SSO adapters. `/api/v1/openapi.json` describes the initial public integration surface.

## Session and concurrency contract

Register with `{email,password,name}` at `POST /api/v1/auth/register`; passwords require at least 12 characters. Login uses `{email,password}`. Both return `{user,organization,role,csrfToken}` and set an HttpOnly, SameSite=Lax cookie. Production requires HTTPS and uses Secure cookies. Include the returned CSRF token as `X-CSRF-Token` on authenticated mutations. `GET /auth/session` refreshes the client’s identity/token state. Passwords use salted scrypt and session tokens are stored as hashes.

Authenticated session responses also include `platformAdmin`. This is separate from workspace membership: creating a workspace makes someone its owner, never a platform administrator.

Project reads and saves return `{project,version,organizationId,access}`. Updates must supply `{project,expectedVersion}`. Conflicts return HTTP 409 without changing the saved project. Scenario command requests also supply `expectedRevision`. The baseline is immutable after initial save. Undo is represented by a new revision rather than moving the revision number backward. Server audit records are separate from the client’s undo history.

Every project save includes a frozen copy of its source baseline. Public snapshots freeze that baseline, scenario, and metric results. Shared views must use the returned `place`, not fetch the current place catalog. Public responses omit internal comments, audit history, organization identifiers, and credentials. Owners can revoke links.

Existing browser drafts must send `{project,baselineHash}` when creating their first cloud save. The server resolves that exact current or archived source; unknown hashes are rejected instead of silently using the latest data. Every new cloud project receives a fresh server ID; clients must adopt the returned `project.id`, including when restoring an exported draft. This prevents retained history from a deleted project attaching to another project. `{placeId,name?}` creates an intentionally new project from the current catalog. `GET /projects/:id` returns `{project,version,baseline,baselineIdentity,organizationId,access}`; the project list contains lightweight metadata only. Reopen the returned captured baseline with the project. A subsequent save can include `baselineHash` alongside `expectedVersion`; a mismatched baseline is rejected. Ingestion archives immutable source bundles under `public/data/snapshots/<sha256>.json` before refreshing the current bundle.

Exports use `/projects/:id/exports?format=pdf|docx|csv|retail-csv|workforce-csv|xlsx|geojson|records&scenarioId=...&revision=...&version=...`. Both optional scenario revision and saved project version are checked before generation; stale requests return 409. The response includes `X-Scenario-Revision` and `X-Project-Version`. The records JSON includes the captured project version, frozen baseline/results, complete private comments/replies, audit, current sharing roster, and public feedback. These records are captured together in one authorized store read, preventing concurrent saves or thread changes from mixing snapshots. PDF/Word reports include a decision brief, paired before/after plan maps, human-authored proposal notes, full scorecard, baseline/proposal assumptions, methodology, source attribution, and input digest. Images are generated from that same authorized saved snapshot with `report-maps.ts`; the API accepts no client image payload or external image URL. Both panels share one projection and frame, preserve exact study-area holes/components, and label changes and source limitations. Reports bind each image to its PNG hash, source hash, scenario ID/revision, and pair-input hash. Additional response headers are `X-Report-Renderer`, `X-Report-Map-Input`, `X-Report-Baseline-Image`, and `X-Report-Proposal-Image`. A stale version is rejected before images are generated. XLSX exports contain typed numeric cells in Read me, Scorecard, Methods, Assumptions, and Sources. Building geometry/program records additionally receive Building programs and Building components sheets; legacy-only workbooks retain their prior layout. These are fixed run outputs, not a second spreadsheet implementation of the model.

Localized edits produce a shared detail frame with at least 400 m of context and an overview showing its position within the complete study area. Widespread changes or unchanged scenarios use the full study area. Both figures retain the same frame and scale; this framing never changes the analytical boundary or scorecard scope. Exact study-area and frame clipping preserve holes and multipart components.

Report-map output is fixed at **1400 × 900** pixels per panel. Admission allows at most **60,000 materialized features per panel**, **750,000 coordinate vertices**, **24 MiB of combined SVG**, and **200 source records**. Exceeding a limit returns `422 REPORT_MAP_LIMIT`; geometry and attribution are not silently dropped. One pair renders at a time per process, with at most two queued pairs and a 15-second queue deadline. A full queue returns `429 REPORT_MAP_BUSY`; an expired queue wait returns `503 REPORT_MAP_QUEUE_TIMEOUT`, both with `Retry-After: 10`. This bounds current rendering work without a paid priority tier; it is not a production throughput guarantee. No licensed aerial imagery is included in these plan figures.

`scenario.details` is a reversible command containing `{name,description}`. Names allow up to 240 characters and descriptions up to 10,000. It advances the scenario revision and remains subject to project roles and locked-baseline protection.

## Project sharing and saved review

New saved projects are private to their creator and explicit project members. A regular workspace owner retains administrative access to every project in that workspace; member responses disclose this exception. Roles are `owner`, `editor`, `commenter`, and `viewer`. All can read/export the project. Owners manage access, delete, publish, and revoke public links; editors can change project content and review any thread; commenters can post/reply and resolve their own threads; viewers cannot mutate content or reviews. Every project route resolves effective project access independently of the session's broader workspace role.

Legacy records without an ACL retain their existing regular workspace access. The first project-member change copies those current workspace roles to explicit grants, then applies the requested change. Subsequent workspace additions receive no automatic project grant. At least one explicit project owner must remain, including when workspace administrators also have implicit access. ACL changes have a separate `aclVersion` and do not increment the saved content version. Role changes and removals are audited and apply immediately to existing sessions.

New sharing uses a pending, emailed invitation. The inviter must have a verified email and current owner authority. The recipient signs in with the exact invited, verified address, reviews the destination and role, and explicitly accepts before access is granted. Registration alone and opening a link grant no access. When needed, acceptance creates a `project-only` membership that lets the recipient select that workspace through `GET /organizations` and `POST /auth/organization` with `{organizationId}`. It grants no access to sibling projects, workspace member administration, or creation of workspace projects. Project-only editors can stage imports only for an authorized project. Import commits remain restricted to the uploader. Removing the last project grant removes this limited membership and moves active sessions to another membership, if available. Regular workspace membership is unaffected.

- `GET /projects/:id/access` returns `{projectId,organizationId,version,access}` without transferring baseline data. Refresh permission metadata independently; never silently adopt a new expected content version over local unsaved edits.
- `GET /projects/:id/members` returns `{access,members,organizationAdmins,disclosure}`.
- `POST /projects/:id/members` now rejects new grants with `409 INVITATION_REQUIRED`; use the invitation endpoints below. `PATCH /projects/:id/members/:userId` takes `{role,expectedAclVersion}`; `DELETE` takes `{expectedAclVersion}`. Stale membership writes return 409. Successful self-removal can return `{access:null,accessRevoked:true,...}`.
- `GET /projects/:id/comments?scenarioId=...` returns the selected saved scenario's current revision, project version, access, and threads even when the list is empty.
- `POST /projects/:id/comments` takes `{scenarioId,expectedRevision,expectedVersion,text,target?,idempotencyKey}`. Target is `{kind:'project'}`, `{kind:'building',id}`, `{kind:'metric',id}`, or `{kind:'location',position:[longitude,latitude]}`. Buildings and metrics must exist in the saved scenario; locations must lie inside its exact frozen study area, excluding holes. Labels and map positions are captured server-side.
- `POST /projects/:id/comments/:commentId/replies` takes `{text,expectedRevision,expectedVersion,idempotencyKey}`. Each reply records the saved revision on which it was posted. Root comments and replies accept up to 10,000 characters. Identical retry keys create no duplicate; a reused key with different content returns 409.
- `PATCH /projects/:id/comments/:commentId` takes `{resolved,expectedThreadVersion}`. Resolution/reopening uses optimistic thread versions and retains audit history. Resolved threads must be reopened before new replies.

New threads/replies require the current saved project version and scenario revision. Threads from an older scenario revision remain visible as stale rather than being presented as current evidence. Legacy comments lacking a saved revision are explicitly unverified and receive no asserted map pin. Saving changed scenario content without advancing its revision is rejected. Deleted scenario identifiers referenced by review history cannot be reused, even with a higher revision; create a new identifier to keep old reviews attached only to their original scenario. The server derives actor identity from the authenticated session, not a client-supplied author field. Public snapshot responses never expose these private review records.

## Email verification, recovery, and invitations

All account features remain free. Registration creates an unverified account that can save its own work. Existing memberships, grants, projects and legacy credentials remain intact; existing accounts are never silently marked verified. The browser exposes **Account security**, **Forgot password?**, and pending invitation controls in **Team**. Invitation acceptance leaves the current project and local draft in place; workspace switching is an explicit next action.

- `GET /auth/security` returns verification and delivery capability, with no queued bodies or tokens.
- `POST /auth/email-verification/request` queues a single-use, 24-hour verification challenge; `POST /auth/email-verification/confirm` accepts `{token}` only while signed in to that exact account.
- `POST /auth/password-reset/request` accepts `{email}` and returns a generic accepted response for eligible, missing, and rate-limited accounts. Delivery configuration is a global capability. `POST /auth/password-reset/confirm` accepts `{token,password}` within 30 minutes. It atomically replaces the password, verifies that mailbox, advances the credential generation, consumes the challenge, and revokes every existing session and outstanding account challenge. It never logs the user in automatically.
- `POST /auth/password/change` requires the current session, CSRF token, and `{currentPassword,password}`. It has the same atomic revocation behavior. Password-change notifications are best effort; recovery does not fail if a notification cannot be queued.
- `GET/POST /projects/:id/invitations` lists or creates pending invitations. Creation requires `{email,role,idempotencyKey,expectedAclVersion}`. The equivalent workspace endpoint is `/organization/invitations`, without an ACL version. Project-only invitations do not grant sibling-project access.
- `POST .../invitations/:invitationId/resend` and `/revoke` require `{expectedVersion}`. Resend rotates the token/version; old links stop working. An invitation is not an access grant.
- `POST /invitations/preview` accepts `{token}`. Only the matching authenticated, verified recipient can see destination details. `POST /invitations/accept` additionally requires `{expectedVersion,expectedAclVersion?}` and rechecks the invitation, inviter authority, target and recipient atomically.

Links use a fixed server-owned HTTPS `APP_ORIGIN` and a URL fragment. The browser removes the fragment immediately, retains the intent only in memory, and performs no mutation until the user submits. Challenge/invitation tables retain token hashes; queued mail bodies use AES-256-GCM with authenticated immutable metadata. Raw tokens, bodies, SMTP replies and passwords are excluded from application audit output. Ordinary web/database roles cannot read sealed mail; the worker may decrypt only its exact currently leased row. SQLite and PostgreSQL enforce the identity transitions; PostgreSQL deployments require migrations **011/012** and the existing restricted authentication/worker logins.

External email is **disabled by default**. To enable it, configure the settings documented in `.env.example`: a verified sender, SMTP host/authentication, canonical HTTPS origin, an active encryption key and a separate stable recipient-hash key. Both keys are 32 cryptographically random bytes encoded as base64. Generate and store them privately; do not paste them into chat or source control. Preserve old encryption keys in `IDENTITY_EMAIL_PREVIOUS_KEYS` while queued messages still depend on them; keep the recipient-hash key stable so rotation cannot reset recipient quotas. Restoring an outbox without its keys cannot deliver its messages.

SMTP requires certificate-verified TLS (465 or STARTTLS on 587), bounded connections, and a 30-second attempt deadline that closes the actual socket. A durable lease admits one delivery at a time, with at most three attempts per message. Default admission caps are 500 queued messages, 500 new messages per rolling day, ten per recipient per rolling day, and a 60-second recipient cooldown; SMTP attempts also have a global daily cap. A crash after provider acceptance can result in a duplicate message: tokens remain single use and retries use a stable message ID. Delivery confirmation means SMTP acceptance, not inbox placement.

Each SMTP attempt reserves the operator-configured positive integer `IDENTITY_EMAIL_MAX_ATTEMPT_CENTS` before dispatch and rechecks the admin budget immediately before sending. Paused processing, a missing/stale administrator cost review or insufficient headroom prevents dispatch. Undispatched cancelled holds are released; started, rejected or uncertain attempts retain their maximum cost until actual invoice reconciliation. SMTP acceptance never invents an actual charge. Include fixed sender/subscription/hosting fees in the existing admin fixed-cost reserve or ledger; configure provider-side spending limits too. This is integrated application admission, not a guarantee of a cloud invoice ceiling.

Reconcile delivery charges with the trusted operator CLI, selecting the target explicitly. `--list` returns only running hold IDs, maximum cents, and attempt keys:

```bash
corepack pnpm exec tsx scripts/reconcile-identity-mail.ts --list --state /absolute/path/to/state.json
corepack pnpm exec tsx scripts/reconcile-identity-mail.ts --invoice /private/invoice.json --state /absolute/path/to/state.json
# PostgreSQL: use --database instead of --state and supply the restricted DATABASE_WORKER_URL.
```

The invoice file is `{"reference":"provider-invoice-and-period","totalCents":5,"entries":[{"reservationId":"existing-running-hold-id","actualCents":5}]}`. Allocate the provider's actual usage total exactly in integer cents across the matching attempts, including zero allocations if the invoice supports them. Fixed fees belong in the separate fixed-cost ledger. The tool atomically settles those holds and records the invoice reference; it does not add a second expense for the invoice total. Identical replays are harmless, conflicting allocations are rejected, and any charge above its bound pauses paid processing for review. Do not also record the same usage as a manual expense. No invoice feed is connected automatically.

The runtime can use an explicitly injected local test sink. This mode is never enabled by the production environment factory and has no public mailbox/token endpoint. Local tests exercise real encryption, leases and account flows without sending external email. Real sender reputation, DNS authentication, provider billing and deployed deliverability remain operator validation work. Enterprise SSO and MFA remain separate unfinished capabilities. The flow follows the [OWASP password-recovery guidance](https://cheatsheetseries.owasp.org/cheatsheets/Forgot_Password_Cheat_Sheet.html) and [email-verification guidance](https://cheatsheetseries.owasp.org/cheatsheets/Email_Validation_and_Verification_Cheat_Sheet.html).

## Legacy GeoJSON imports

The current browser uses the project-bound GIS workbench below. This earlier endpoint remains for compatibility. New uploaded sources default to private use; `publicRedistribution:true` explicitly declares permission for public sharing.

POST `/imports/geojson/preview` with `{layer,projectId,scenarioId?,sourceName,geojson}`. `layer` is `buildings`, `parcels`, or `blocks`; omission selects building import. Parcel/block previews require a saved `projectId`; `scenarioId` defaults to the active alternative and cannot be Baseline. Optional source fields for every layer are `sourceUrl` (HTTP(S)), `sourceVintage`, and `sourceLicense`. A building preview may still be unbound when `projectId` is omitted; commit always rechecks geography.

The response includes `{importId,expiresAt,extentChecked,layer,source,warnings,featureCount,requiresReview:true,committed:false}` plus `buildings` or `parcels`. Previews expire after 24 hours. POST `/projects/:id/imports/:importId/commit` with `{scenarioId,expectedRevision,expectedVersion,acknowledgeWarnings}` to apply the reviewed layer. One `buildings.import` or `parcels.import` command preserves its manifest and creates one undo step. Retrying an identical committed import does not duplicate geometry. The wizard refreshes its preview when the target changes; commit reauthorizes the uploader, verifies the project/scenario versions, and validates the target's current geometry.

Building, parcel, and block layers accept WGS84 **Polygon and MultiPolygon** geometry with all holes and separate components retained. Each ring supports 500 editing points plus closure; each feature supports 5,000 vertices including closures. An import permits at most 5,000 features and 50,000 total vertices; the resulting scenario permits 5,000 combined parcel/block features. Same-kind boundaries may share edges but not land area. Blocks may overlap parcel land and are excluded from parcel metric denominators. A bounding-box sweep limits exact overlap checks to 50,000 candidate pairs. Invalid/outside geometry or excess complexity is rejected without truncation or simplification.

Imported parcel/block features receive new internal `parcel-<UUID>` identifiers; imported buildings receive `import-<UUID>` identifiers. The original GeoJSON `Feature.id`, or explicit `properties.parcelId`, is retained separately as `sourceFeatureId`; it is bounded text, not an internal object key. Names and source references are limited to 240 characters. Source name, URL, vintage/license when supplied, uploaded provenance, and import lineage remain available in saved records and exports. Ownership, tax, zoning, and other attributes are not silently mapped or certified. Missing height, floors, units, jobs and parking values remain null with missing-field provenance; supplied zero remains zero. Building use must be explicitly reviewed or mapped. The legacy GeoJSON route no longer invents estimates for absent quantities. Building imports preserve complete geometry and accept supported scalar attributes, typology, and an exact `properties.program` object. Component source IDs and rate source IDs are bound to the actual uploaded source; supplied claims of observed authority are not inherited. External building references use `Feature.id`, then `properties.sourceFeatureId` or `properties.buildingId`. Use and units/jobs omitted from the outer properties are derived from the program; contradictory supplied mirrors are rejected. No ownership, zoning, tax value, or entitlement is inferred.

## GIS/CAD review and Shapefile export

The five-step workbench accepts GeoJSON, Shapefile ZIP and closed-footprint DXF through a saved project. A free signed-in editor uploads original bytes, inspects layers, explicitly reviews coordinates/units and fields, declares source rights, then prepares a complete immutable preview. Apply records one reversible command. Append and exact matched updates are separate choices; unmatched, duplicate or ambiguous targets reject the batch. The previous legacy route is not a substitute for the native CRS/CAD review flow.

All routes below are under `/projects/:projectId/imports` and require the uploader's current editor/owner access. Writes require CSRF. Metadata always precedes the single file part in a multipart upload.

- `GET /capabilities` reports availability and fixed-capacity policy.
- `POST /uploads` accepts multipart `metadata` (`scenarioId`, `expectedVersion`, `expectedRevision`, `idempotencyKey`) and `file`; it returns an inspection job with HTTP 202.
- `GET /jobs`, `GET /jobs/:jobId` and `GET /uploads/:uploadId` expose owned job status and completed inspection. `POST /jobs/:jobId/cancel` and `POST /jobs/:jobId/retry` implement explicit recovery.
- `POST /uploads/:uploadId/preview` accepts the version-bound submission, conversion recipe, field mapping and source declaration; `GET /jobs/:jobId/preview` returns the exact prepared geometry, hash, diagnostics and changes.
- `POST /:importId/commit` requires `scenarioId`, `expectedVersion`, `expectedRevision`, `previewHash` and `acknowledgeWarnings:true`. The response includes the saved project/version and verified organization/access receipt. Replaying the same receipt cannot apply twice; stale content rejects with 409.
- `GET /uploads/:uploadId/file` downloads the original source; `POST /exports/shapefile` freezes the saved scenario/version/revision into a queued export; `GET /jobs/:jobId/download` returns the completed ZIP with a SHA-256 ETag. Access is rechecked after archive reads.

The complete exchange ZIP contains separate geometry layers, explicit DBF null/status fields, a field dictionary, and exact JSON sidecars for nested programs, source records and identifiers. Use full project records JSON for restoration of complete scenario/history state; reimporting Shapefile geometry does not reconstruct that entire state.

Project format **8** preserves nullable height/floors/units/jobs/parking, quantity provenance, source import/rights metadata and explicit append/match commands throughout current and historical states. Older untouched bundles retain their original bytes. Model **0.7.0** withholds totals and deltas that depend on unknown quantities and separately labels mathematically valid known subtotals; null never becomes an observed zero. Existing frozen retail and workforce captures keep their own evidence/method identities.

Native processing is off by default. It requires the installed pinned offline GDAL image, migrations 006/007, private persistent storage, declared fixed capacity, and administrator budget headroom. No paid provider is activated. Full-project saves cannot silently erase prior source-rights declarations, and publication checks retained history/commands as well as current inventory. Failed admission rolls back newly staged source bytes; uncertain database acknowledgments retain potentially referenced evidence. Queue scans load lightweight headers and fetch the full payload only for the selected job. The configured $300 monthly allowance remains administrator-adjustable and does not itself cap external provider invoices.

See [GIS runtime and operating limits](../../docs/GIS_RUNTIME.md) for exact format support, provenance, archive recovery, resource limits, installation and verification. Traffic-count tables, scanned site plans, cadastral certification, automatic retention cleanup and production capacity validation remain outstanding.

## Building geometry and programs

Buildings retain either the unchanged legacy `{footprint}` ring or complete `{geometry}` Polygon/MultiPolygon, never both. New geometry area is derived from all components minus holes; unchanged captured geometry is preserved byte-for-byte. The `building.upsert` command accepts optional `sources: Source[]` and validates exact study-area containment. Current scenario states and every historical undo/redo target are validated against the frozen baseline before a full save. Internal building/road/parcel identifiers reject reserved object-property names; external source references remain bounded text.

An optional `program` contains `{version:1,grossFloorAreaSqm,commonAreaSqm,components}`. Each component has `{id,use,grossFloorAreaSqm,units,jobs}` plus optional name, beds, residential subtype, source ID, and trip/parking rates. A rate is `{value,basis,sourceId}`; supported bases are dwelling, occupied-dwelling, 1000-sqft, job, and bed. At most 64 components are accepted. Component floor areas plus common area must equal declared total, and top-level units/jobs mirror component totals. Top-level use equals the sole component use or mixed-use when component uses differ. Programs do not rescale automatically when geometry changes. Entered gross floor area may differ from footprint × floors, with an explicit discrepancy/massing warning; parking supply remains separate from calculated demand. Program types, zero-area parks/vacant land, and basis-specific required quantities are validated by the shared schema.

Project format **3** is required when geometry/program/typology extensions occur in a captured baseline, current state, command, or history. The API reads unchanged formats 1 and 2 and rejects any saved-format downgrade with `409 PROJECT_VERSION_DOWNGRADE`. Baseline identity remains unchanged; no empty building extension fields are inserted into legacy source bundles. Saved/public/GIS records preserve complete geometry, programs, provenance, and source references. Reports draw actual courtyard holes and detached parts while counting one building feature once. New report appendices expose component allocation, rates, sources, and uniform-height limitations. PDF/Word inventories reject above 500 extended building records across baseline/proposal or 2,000 component rows; XLSX rejects above 20,000 rows. No oversized report is silently truncated; full records and GeoJSON remain available.

## Parcel commands and format compatibility

Existing revision/version-bound scenario commands additionally accept:

- `parcel.upsert` with `{parcel,source?}` to draw or reshape one boundary.
- `parcel.remove` with `{id}` to remove the boundary without deleting buildings.
- `parcels.replace` with `{operation:"split"|"assemble",removeIds,parcels,source}` for one atomic subdivision/assembly edit.
- `parcels.import` with `{parcels,source}` for a reviewed layer.

All parcels contain `{id,name,kind,geometry,sourceId}` with optional `geometrySourceId`, `sourceFeatureId`, and lineage. `kind` is `parcel` or `block`. Split/assembly must preserve the original land, holes, feature kind, and provenance; output IDs must be new. The interactive splitter uses a straight line and creates one lot per resulting connected component. Assembly may return a disconnected MultiPolygon, explicitly labeled. Source geometry is never buffered into a missing strip or silently repaired. The shared validators reject malformed geometry, same-kind overlaps, no-cut/sliver results, and invalid replacement lineage. `INVALID_PARCEL_EDIT` returns 422 for command/extent failures; schema errors are rejected before storage. Internal parcel identifiers and edit keys exclude reserved object-property names; source feature references remain separate bounded text.

Project format **2** is required once parcel fields or parcel history are present, including a captured parcel baseline. The current server continues to read unchanged legacy format 1. Upgrade persists after undo/restore so older clients cannot silently drop parcel fields; replacing an existing format-2 project with format 1 returns `409 PROJECT_VERSION_DOWNGRADE`. This does not change the baseline-identity algorithm or inject empty parcel arrays into legacy captured places. Full saves validate both active scenario states and historical undo/redo snapshots against the frozen study area. Saved/public/GIS/report inputs retain complete parcel geometry, original source references, and lineage.

Building-authoring verification is complete for this checkpoint: 378 unit/integration tests passed across 43 files, including 40 live PostgreSQL checks (22 security, 14 storage, and 4 API workflows). Browser verification covered 23 distinct workflows across the final 3-building-workflow and 20-regression-workflow batches, plus 4 final visual-regression flows; these were separate runs, not one combined suite. All 35 PDF pages and 27 canonical-rendered Word pages were visually reviewed with no material layout defects; minor number-formatting and continuation-color observations are retained in the review records. The structural audit found no text outside page/safety bounds or body/footer overlap, verified both embedded map hashes, and found no issues in its limited DOCX accessibility checks. Evidence is retained under `.local/qa/buildings/`, including `report/structural-review.json` and the visual review records. These checks cover the saved fixtures and workflows; they do not certify production load, model calibration, full accessibility compliance, or tagged-PDF output.

## Activity controls and household vehicles

Project format **5** preserves optional `Scenario.activity` controls and optional frozen `Place.vehicleAvailability`. Old formats 1–4 remain unchanged. Format upgrades are monotonic even after removal, undo or history retention; saving an older format over an existing format-5 project returns `409 PROJECT_VERSION_DOWNGRADE`. No new fields are backfilled into existing source bundles.

`POST /projects/:id/scenarios/:scenarioId/commands` accepts `{command:{type:"scenario.activity",activity,sources?,horizon?},expectedVersion,expectedRevision}`. The activity object contains references, global absolute/year-zero-percent targets, population/employment allocation methods, up to 100 exact Polygon/MultiPolygon neighborhoods (including holes), optional forecast/preset provenance, and reviewed demand-response choices. `null` removes the controls. Optional horizon is 0, 5, 10 or 20 and is committed atomically with the edit. The usual owner/editor ACL, CSRF, audit and optimistic conflicts apply. The baseline scenario cannot be edited. Current, historical, undo and command-only historical payloads are checked for source references, geometry, exact study extent and disjoint area interiors; no silent repair or feature omission occurs.

Population may use a matching published whole-ZCTA estimate, a housing-supported reference, or an explicitly sourced entered count. Workplace employment has no observed adapter and therefore uses building-derived or entered evidence. Household vehicles use a matching captured/published B25046 reference or a sourced entered count; building counts, daily trips and decorative map agents never stand in for vehicle stock. Missing references permit absolute targets but leave unsupported percentages/deltas or demand responses unavailable. Targets apply at the selected horizon without compounding growth again. Neighborhood targets replace their allocated counts as local exceptions; they do not redistribute the remainder or rewrite building capacities. Proportional demand is an explicit reviewed sensitivity. Household-stock response replaces the residential population response rather than multiplying both.

`GET /projects/:id/vehicle-reference` is a read-only project-ACL-protected route returning `{projectId,organizationId,projectVersion,baselineHash,status,reference,reason?}`. Private project routes are scoped to the current project ACL:

Complete project records additionally retain excluded/superseded responses and moderation history.

### Dashboard API

Only a signed-in platform administrator can call these endpoints. Writes require the session CSRF token and trusted origin. Types are defined in `packages/core/src/budget.ts`.

- `GET /api/v1/admin/budget` returns the current policy, UTC month, exact cent totals, admission status, coverage disclosures, recent records and the versioned cost outlook. It records a changed observed alert state; this is not background monitoring or notification delivery.
- `PATCH /api/v1/admin/budget` accepts `{expectedVersion,monthlyLimitCents,safetyMarginCents,fixedCostReserveCents,paidOperationsPaused}`. All amounts are integer USD cents. It returns the complete dashboard. Stale versions return 409; reductions below existing obligations immediately prevent new admission and dispatch, while preserving the obligations. A fixed reserve above the ceiling is permitted and shown as exhausted budget.
- `POST /api/v1/admin/budget/adjustments` accepts `{idempotencyKey,amountCents,category,reason}` for the current UTC month. Category is `fixed` or `variable`. Positive amounts record invoices; negative amounts correct/refund previously recorded costs and require a reason. Corrections cannot take a category below zero. Retrying the same key and values creates no duplicate; changing values for a used key returns 409. A delayed retry after month rollover keeps the original record in its original month.
- `POST /api/v1/admin/budget/reviews` accepts `BudgetCostReviewInput`: an exact `expectedBasisHash`, UTC coverage/expiry, estimated unresolved unreported costs, ordered future low/expected/high amounts, evidence statement, preceding review ID and explicit prior-cost acknowledgement. The immutable review returns the updated dashboard; stale evidence returns 409. The default form expiry is 24 hours, bounded by month end; the maximum is seven days after coverage and no later than the next UTC month.
- `GET /api/v1/admin/budget/records?collection=adjustments|reservations|audit|costReviews&cursor=…` returns complete newest-first records across all months, 50 per page. An optional opaque cursor binds the collection snapshot. A changed collection returns `409 BUDGET_RECORDS_CHANGED`; invalid cursors return `422 BUDGET_CURSOR_INVALID`. This read adds no audit observation.

Accounting avoids double counting:

```text
recorded spend = fixed invoices + variable invoices + settled operation costs
remaining fixed allowance = max(0, fixed reserve − fixed invoices)
accounted = recorded spend + remaining fixed allowance + open maximum-cost reservations + unresolved unreported estimate
safe available = max(0, monthly ceiling − safety margin − accounted)
```

For example, a $50 fixed reserve and a recorded $20 hosting invoice consume $50 in total, leaving $30 of the reserve for other fixed charges. Recording $60 in actual fixed bills consumes $60. `overLimitCents` compares all accounted obligations with the monthly ceiling; admission stops earlier at the ceiling minus its safety margin. The initial zero fixed reserve means it has not been configured, not that infrastructure is free. Audit history records policy changes, entries, reviews, reservations, dispatch, reconciliation, release and observed alert transitions. The dashboard's latest-100 preview is supplemented by the complete paginated records endpoint.

The cost review's unreported estimate remains held across expiry, changed evidence and UTC month rollover until an explicit replacement reconciles it. Missing, stale or invalid reviews withhold the outlook and block new costly work. Manual entries, fixed-reserve changes and overruns invalidate coverage; normal integrated reservation lifecycles do not. Low/expected/high scenarios use captured accounting plus authored future costs, floored by live accounted exposure. They are not statistically estimated forecasts or independently verified bills. See [the complete method, workflow and limitations](../../docs/BUDGET.md).

### Paid adapter contract

`BudgetService` is a trusted server API, not an ordinary-user HTTP endpoint. A future provider adapter must use an upper-bound integer-cent estimate, include taxes/fees/usage limits, and obtain a reservation before doing external work. Browser-supplied cost estimates are never sufficient. `reserve` is atomic and idempotent; `start` must succeed exactly once immediately before external dispatch. Use the same operation key with the provider’s idempotency mechanism where supported. A repeated `start` is rejected, so a request retry cannot issue the external call again. Distributed dispatch still requires a durable worker/outbox and provider reconciliation before enabling real paid work.

After a provider result, `settle` replaces the reservation with the actual cost atomically, even if actual cost exceeds its estimate. An overrun automatically pauses further paid work and increments the policy version for administrator review. Repeated identical settlement creates no duplicate charge. Costs are recognized in the UTC month when reconciled. `release` is for cancellation before dispatch or a confirmed zero-charge result; for partial charges, settle the actual amount. Never release a running reservation merely because a request timed out.

Only undispatched reservations expire. Running work remains held across UTC month boundaries until reconciled, so a timeout or monthly reset cannot restore spendable capacity for an unknown charge. New months reset the current-month recorded costs and renew the fixed allowance; unresolved running holds continue to count conservatively. When providers are integrated, reconcile their billing periods and feed actual invoice corrections through the ledger.

The development adapter uses SQLite transactions. PostgreSQL serializes budget changes through its advisory write gate and serializable transactions, including across independent API connections. SQLite guards and PostgreSQL migration **018** enforce immutable review/audit/ledger history and reservation lifecycle constraints under runtime roles; preparation workers can read budget evidence but cannot write it. Apply migration 018 through the separate operator connection before starting the updated PostgreSQL runtime. The ledger is stored independently of projects and baselines; it remains a single global budget record.

## National place search and bounded preparation

Search is explicit-submit only; it does not send requests for each keystroke. ZIP searches use the official [Census TIGERweb 2020 ZCTA layer](https://tigerweb.geo.census.gov/arcgis/rest/services/TIGERweb/PUMA_TAD_TAZ_UGA_ZCTA/MapServer/1), city searches use Census incorporated-place/CDP reference points, and full street addresses use the [official Census Geocoder](https://geocoding.geo.census.gov/geocoder/Geocoding_Services_API.html). Address positions are approximate address-range matches. A city or address result locates its containing ZCTA; it does not silently prepare an entire city.

[ZCTAs are Census statistical approximations of postal ZIP areas](https://www.census.gov/programs-surveys/geography/guidance/geo-areas/zctas.html). Some postal ZIPs have no corresponding ZCTA. The system preserves exact Census Polygon/MultiPolygon components and holes, and reports an unsupported area rather than discarding islands or simplifying the analytical boundary. Roads are fetched with a 100 m buffer and clipped to the exact study area; the buffer does not enlarge it. Footprints crossing its boundary are excluded and disclosed, rather than modeled as partial buildings. OSM complex building/park relations are currently omitted and disclosed; mapped ways are not a complete building inventory. Attribute estimates are labeled and use the same shared inference module as future Phoenix reference ingestion.

Public routes:

- `GET /api/v1/places/search?q=85004` returns `{mode,candidates,warnings,attribution}`. Candidate fields are `{id,label,kind,coordinates,zip?,placeId?,prepared,detail,sourceName}`. The `kind` is `zcta`, `city`, or `address`.
- `GET /api/v1/places/locate?lon=-87.622&lat=41.886` finds the exact containing Census ZCTA for a selected city, address, or map point.
- `GET /api/v1/places/preparation-capabilities` reports current enablement and hard limits. Existing `/places` and `/places/:id` expose prepared bundles without sign-in.

New preparation requires a free authenticated account and CSRF token:

- `POST /places/preparations` with `{zip,idempotencyKey}` returns `{job}` (202 queued, 200 already prepared).
- `GET /places/preparations` lists the current account’s recent jobs; `GET /places/preparations/:id` returns its private progress.
- `POST /places/preparations/:id/cancel` requests cancellation; `POST /places/preparations/:id/retry` with a new `{idempotencyKey}` retries a transient failure explicitly. Size/coverage failures are not automatically retried. Each job permits at most three attempts.

Jobs preserve status, milestones, attempt count, cancellation, warnings, and result identity in the durable store. A transactional lease allows only one active worker across API instances sharing that store. The worker renews its 180-second lease every 15 seconds. Interrupted jobs are recovered on restart/next worker scan. Cancellation aborts a local source request immediately; another worker observes it on heartbeat. A complete source download is cached for 24 hours before conversion, so geometry fixes and repeated requests can reuse it. Source timeouts, runtime remarks, missing completion counts, oversized responses, and invalid geometry fail explicitly. A complete bundle and provenance are written to content-addressed `public/data/snapshots`, `sources`, and `manifests` before the current place pointer is published.

This is a **bounded public-source pilot**, not complete national preprocessing: maximum 50 km² study area, 75 km² buffered fetch envelope, 40,000 source features, 500,000 OSM vertices, and 25 MB response; three new area requests per account per UTC day, ten total preparation attempts per UTC day, a minimum 60 seconds between attempts, and one active job. Requests beyond those bounds explain that regional preprocessing is needed. Search is limited across the application, and official-provider requests are serialized/cached. URLs are fixed server-side, redirects are rejected, and users cannot supply a provider endpoint. No paid data provider is configured or activated.

`NATIONAL_PUBLIC_PREPARATION_ENABLED` defaults to enabled in development and disabled in production. Actual preparation also requires `NATIONAL_CAPACITY_STATEMENT` (12–1,000 characters), `NATIONAL_CAPACITY_ENVIRONMENT=local-development|deployment`, a current administrator cost review, an unpaused policy and budget headroom. Production accepts deployment capacity only, with a fixed reserve or recorded fixed costs. The same checks run before a new source attempt; a queued attempt blocked by changed evidence fails as retryable before using source quota. Refresh the cost review, then explicitly retry. A trusted operator may enable the flag for a bounded production pilot. The [Overpass operator’s guidance](https://dev.overpass-api.de/overpass-doc/en/preface/commons.html) warns that public instances are not a sustainable backend for general-purpose applications. Broad launch requires regional extracts or dedicated ingestion with independently enforced resource and vendor budgets. Turning off preparation preserves free search and existing prepared places. Infrastructure charges remain subject to the operating-budget limitations above.

Isolated QA may instead explicitly declare `local-development`, which is labeled **not production cost validation**. Never change production budget state for tests. Jobs preserve CPU/time limits and elapsed attempt observations separately from money. Budget pause or exhausted headroom stops queued starts.

All routes are under `/api/v1/projects/:projectId/workforce`. Existing project ACL rules apply: viewers/commenters can inspect authorized jobs and results; editors/owners can submit, cancel, retry, and adopt. A grant to one project creates no access to another project's jobs or archives. Mutations require the session CSRF token.

- `GET /capabilities` reports source configuration, exact supported modes, prepared-region extent, bounded capacity, and cost limitations.
- `POST /jobs` takes `{scenarioId,expectedVersion,expectedRevision,idempotencyKey,request:{site:[longitude,latitude],mode:"car"|"walk",direction:"inbound",thresholdsMinutes:[15,30,45]}}`. It returns `{job}`. A matching retry of the same submission returns its original job; reuse for different inputs returns 409.
- `GET /jobs` and `GET /jobs/:jobId` return lightweight progress and retained attempt history. Progress is coarse processing stage, not an ETA. No raw origin rows or large source packs are transferred.
- `POST /jobs/:jobId/cancel` takes `{expectedJobVersion}`. `POST /jobs/:jobId/retry` takes `{expectedJobVersion,idempotencyKey}` and performs admission again. Cancellation and failure never erase consumed attempts.
- `GET /jobs/:jobId/result` returns `{job,workforce,contour,siteSnapMeters}`. Contours are exact separately stored display geometry; numeric counts come from origin-specific routes. The snap value is a distance, not an invented snapped coordinate.
- `GET /jobs/:jobId/artifact` is an explicit authorized download of complete routing rows, aggregation and contours, with `X-Content-SHA256`, private no-store and a three-per-minute limit. It never returns the large cohort source pack. Source URLs and hashes support reconstruction.
- `POST /jobs/:jobId/adopt` takes `{scenarioId,expectedVersion,expectedRevision,inputHash,resultHash}`. One transaction verifies the owning artifact and exact request, applies a reversible `scenario.workforce` command, writes audit history, and advances the project/scenario version. The response includes the saved project, frozen baseline/identity and current access.

One durable lease permits one worker globally. Admission allows ten queued/running jobs, one pending request per account, three starts per account per UTC day, and three attempts per job. A lost lease becomes an explicitly failed, retryable attempt; reopening the app does not silently rerun it. Current project access is rechecked before dispatch, during heartbeats, and before completion. A revoked requester or deleted scenario cannot publish a completed result. Existing queued jobs can drain even when the retained-history admission cap is reached.

Complete raw evidence is atomically written and hash-verified in the private archive before the immutable database artifact and completed job commit together. Limits are 64 MiB per raw artifact and 2 GiB total archive, with free-disk admission; no truncation or automatic deletion occurs. Operator maintenance must preserve needed evidence and backups. An unavailable/corrupt archive blocks fresh download/adoption with an explicit error; already saved summary tables remain intact. The scoped artifact header projection keeps contour geometry out of status polling and ordinary project saves.

Project format **7** persists a compact capture (maximum 256 KiB) and contour reference rather than duplicating raw rows or contours through undo history. Server-run evidence must match the entire project-owned immutable artifact on current, history, undone, and command saves. Caller-provided hashes alone confer no authority. A restored copy converts all envelopes, including history, to explicit `origin:"imported"` while preserving the exact numerical capture, source references and original receipt. Imported evidence is integrity-checked and visibly unverified; it never authorizes access to an original project's private job. Tampering with a server-run capture or presenting another project's receipt as current server verification is rejected.

Published scenarios freeze the compact evidence and its origin label; public views do not gain private archive access. PDF/Word/XLSX/GeoJSON/records and dedicated `workforce-csv` exports retain captured values and source/method identifiers independently of the general impact-model version. Reports label imported evidence and partial/unknown coverage rather than replacing missing observations with zero. Detailed numerical evidence uses its own workforce method version; ordinary building or street edits do not silently recalculate it.

## Captured effective FEMA flood overlays

An operator can prepare complete bounded effective NFHL captures for an exact supplied baseline. The command never changes that baseline or any saved project:

```sh
mkdir -p /private/flood/packs
node node_modules/tsx/dist/cli.mjs scripts/prepare-flood.ts --place /path/to/baseline.json --output /private/flood/packs/new-capture
```

The output directory must be new. The preparer obtains layer metadata, spatial object-ID inventories, every full record in batches, and exact Study_Info records, then repeats the record/ID and Study_Info checks. Changed, truncated, missing, malformed or oversized responses fail closed. These sequential checks establish observed consistency, not a transactional point-in-time guarantee from the upstream service. Raw response bytes are retained by SHA-256; `capture.json` records the complete fenced retrieval before normalization, including failures of the subsequent geometric step. Only a successfully normalized `pack.json` plus `manifest.json` is eligible for registration. Source geometries are clipped to the exact study polygon without simplification or repair; original attributes, dates and full source polygons remain recoverable from the raw archive. Availability, panels, effective LOMRs, seclusions and Study_Info are retained separately. Property-specific letters of map amendment are not applied.

Limits are 32 MiB per response, 128 MiB of total received bytes, 256 receipts, 5,000 raw features and 200,000 raw vertices, with a ten-minute capture deadline. Source normalization, imported-pack topology validation, flood-selected model calculations, document/map exports and GIS manifest preparation share one CPU worker per process. It admits at most two waiting requests, with a 30-second queue deadline, a 60-second execution deadline, 160 MiB task input/output bounds and a 512 MiB V8 old-heap limit (not a hard process RSS cap). Structural parsing remains on the API thread; expensive geometry work is isolated. Successful validation is reused only for the exact complete content hash. The slot is released only after worker termination; unconfirmed termination quarantines that process's slot. Deployments must account for each API process separately. A normalized pack is capped at 8 MiB/50,000 vertices; the configured and project catalogs are capped at eight packs/16 MiB. No records are silently truncated. The source is a published flood-mapping study, not observed flooding or empirical model validation.

Configure a public catalog JSON file beside its confined preparation directories:

```json
{
  "version": 1,
  "datasets": [
    {
      "id": "effective-study",
      "label": "Effective flood mapping · captured date",
      "directory": "packs/new-capture"
    }
  ]
}
```

Loading verifies the immutable raw files, source query identities, repeated inventories, normalization and exact pack hash. Apply migrations 015/016/017 and explicitly install source authority before accepting new trusted project references:

```sh
node node_modules/tsx/dist/cli.mjs scripts/install-flood-catalog.ts --catalog /private/flood/catalog.json --operator-confirm --database-file /private/app/state.sqlite
```

For PostgreSQL omit `--database-file` and supply the existing private `DATABASE_MIGRATION_URL` through the operator environment. Runtime web/auth/worker roles cannot register or rewrite source authority. Set `FLOOD_CATALOG` to the configuration path for the API; an unset variable leaves the public catalog empty. Registration is never performed by API startup. Retire a preparation from runtime configuration rather than deleting its immutable database authority or source archive. Existing exact project-owned references remain valid after retirement; new trusted references require current configuration and exact registered content.

Anonymous GET `/api/v1/flood/catalog?studyAreaHash=<sha256>` lists matching public cached choices; GET `/api/v1/flood/datasets/:hash` returns an allowlisted normalized dataset. Neither endpoint accepts a path/URL or fetches live FEMA data. Local guests can attach evidence and edit normally. The first cloud save validates authority. POST `/api/v1/projects/:projectId/flood/adopt` requires an editor/owner, CSRF, `scenarioId`, `expectedVersion`, `expectedRevision` and `datasetHash`; it installs the catalog entry and history command atomically.

Project format 11 stores each dataset once in `project.floodDatasets`; scenarios and undo history retain only a versioned hash/reference/origin. Existing keys are immutable. Imported copies retain exact data with explicit unverified provenance; a caller-provided `server-catalog` label or digest alone is not authority. Public snapshots freeze only their selected dataset, with public-source permission checks. Private authorized exports do not grant public redistribution. All metric/report calculations receive the selected project catalog; `flood-csv`, records, GeoJSON, XLSX, PDF/Word and Shapefile exports retain the evidence appropriate to their format. Flood exposure describes mapped building-footprint intersection, not probability, depth, loss, safety, insurance or a legal determination. Missing, unmapped or undetermined coverage remains unknown.

The reference also selects its calculation method independently of the source-pack hash. New attachments explicitly select `flood-footprint-1.1.0`; an omitted method always replays `flood-footprint-1.0.0`, as does an explicit legacy selection. A user can change only the method through the existing `scenario.flood` command with expected project version and scenario revision; that edit retains the same source bytes and appends reversible history. Existing public snapshots remain frozen. Unsupported or null methods are rejected by the API, SQLite guard and appended PostgreSQL migration 017; runtime roles now require security version 17.

Retained permissions also survive a new dataset hash. An imported copy cannot silently remove a declaration tied to the same source ID, citation URL or raw-file receipt hash; renaming the source ID alone does not detach that provenance. Saving requires the retained declaration or an explicit complete current attestation. Publication and export independently recheck applicable retained restrictions. An unverified private import does not override the separately verified authority of an exact public operator-catalog capture. Private export snapshots retain the catalog's permission context internally, while the generated Shapefile includes only the selected dataset.

### Private high-resolution media jobs

`GET /api/v1/projects/:projectId/media/context?scenarioId=...` prepares a saved, revision-bound scene for the current editor. The account-scoped preview cache is limited to eight entries, 64 MiB total and five minutes. A scene exceeding 32 MiB is rejected whole; preparation has one process-local worker, no waiting queue, a 60-second deadline and a 512 MiB V8 old-generation heap limit (not an RSS limit). Saved source permissions, complete metric values and independent citation namespaces are retained. No sessions, access lists or comments enter the renderer.

`POST .../media/jobs` binds the returned `sceneHash`, exact `recipe`, `scenarioId`, `expectedVersion`, `expectedRevision` and `idempotencyKey`. List/status, explicit cancel/retry and allowlisted artifact downloads live below the same `/media` path. Completed media and provenance files carry exact hashes and sizes; every download rechecks current project access. Native inputs remain private and are not an HTTP download endpoint. PNG/MP4 exports do not mutate the project or establish a public publication.

`GET .../media/jobs` returns `{jobs,nextCursor}` with at most 100 records ordered by descending creation time and ID. Pass `scenarioId` to filter before paging, and carry the opaque `cursor` with the same project and scenario to retrieve older exports. New jobs appear on refresh; changing a job's status does not change its page position. Each page requires current project access. Structured credential-bearing source URLs and private filesystem locators are rejected during bounded scene preparation; metadata is never silently scrubbed or rehashed. A malformed optional media image setting leaves media unavailable with an actionable capability message while basic application startup remains available.

Current limits are ten pending jobs globally, one per account, three attempts per account per UTC day, three attempts per job and a 900-second native deadline. ## Fiscal profile library and separate studies

Browser-local fiscal authoring is available without an account. Free full-workspace members can read the organization library; owners and editors can append versions. Project-only guests cannot read or create organization library records. No provider or payment configuration is used.

- `GET /fiscal-profiles` lists the latest version of each family. `GET /fiscal-profiles/:profileId/versions` lists every retained version. Both return at most 50 compact headers and an opaque `nextCursor`; send it as `cursor` for the next page. `GET /fiscal-profiles/:profileId/versions/:versionId` returns the exact profile snapshot and its hash.
- `POST /fiscal-profiles` takes `{profile,profileId?,expectedLatestVersionId?,idempotencyKey}`. A first version omits the family/latest IDs; an append requires the current latest version. Versions are immutable. Capacity is 1,000 retained versions per organization and 100 per family, with a 256 KiB profile bound; reaching a limit never deletes older evidence.
- `POST /projects/:projectId/fiscal-studies` takes `{scenarioId,expectedVersion,expectedRevision,name,applicabilityNotes,idempotencyKey}` and exactly one of `libraryVersionId` or `profile`. It requires current source-project editor access and full-workspace owner/editor membership. The response includes the separate project, version, baseline identity and access. Exact-key replay rechecks source and target access and returns the same study; conflicting input returns 409.

New inline source attestations receive the authenticated submitter ID and server receipt time. The original submitted request is the idempotency basis, and the response contains the exact stamped snapshot. Selecting an existing library version preserves its bytes. These are uploader declarations, not independent verification of licenses, coefficients or local fiscal applicability. Every source needs explicit private use, caching, analysis, display and historical-retention permission; export and public redistribution remain separate gates.

A new study freezes the full profile, geography/value-basis review, baseline assumptions and source lineage. It copies only the selected current planning alternative, including its edits and numerical captures, and starts fresh history. The original project and its complete history remain unchanged. Project-owned traffic/workforce/accessibility captures and copied flood references become imported evidence with their source permissions retained; the new project does not acquire their original server authority. Changing a saved study's profile requires another new study. Profile library changes never dynamically alter saved calculations.

Fiscal context travels through saves, immutable publication snapshots, media scene preparation and exports. `format=fiscal-csv` returns the frozen fiscal ledger, and the other report formats retain the corresponding profile and calculation context. Publications and exports recheck their distinct source permissions. No default national tax rate, market-to-assessed conversion, marginal service-cost claim or automatic coefficient acquisition is implied.
