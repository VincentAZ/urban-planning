# Scoped persistence, migration, and recovery

The API stores accounts, workspaces, memberships, sessions, projects, publications, discussions, feedback, imports, audits, preparation jobs, project-owned workforce jobs/artifacts, private GIS jobs, reviewed traffic configurations/uploads/jobs/artifacts, and shared native capacity as independently addressable records. Project/publication metadata is separate from scenario/history payloads and immutable baseline geometry. Baselines use the existing canonical SHA-256 identity and are stored once per distinct source object. A saved project content version is retained independently of its current header and ACL.

Production mode requires PostgreSQL/PostGIS. Local development uses SQLite through Node's built-in `node:sqlite` binding; the `FileStore` class name and `development-file` capability label remain compatible with the earlier development adapter. The binding is experimental in the tested Node 22.22.1 release; the application requires Node 22.13 or later. This does not introduce a paid service or change free access. See the [Node 22 SQLite API](https://nodejs.org/download/release/v22.22.1/docs/api/sqlite.html).

## Request behavior and data boundaries

Runtime API calls explicitly select their identity and record dependencies. Unselected state collections throw on access. Header views have separate types; a project list, access check, publication status, or engagement summary does not receive a placeholder masquerading as a complete map. An authorization decision and its selected records are captured in the same database transaction.

Filtered array replacement deletes only the loaded identities. An append cannot overwrite an unseen existing record. Header updates change only permitted mutable metadata; they cannot replace a scenario, source, or saved result. Full publications retain frozen proposal content and questionnaire definitions. Callback results are detached from persisted state, and callbacks must be synchronous with no external side effects.

Insertion order is preserved explicitly. It determines legacy latest-response selection, stable participant labels, queued job order, and workspace fallback selection; timestamp or UUID ordering is not substituted during migration.

New cloud projects always receive a server-generated ID. A first save or restored draft must adopt the returned ID. Deleted project IDs remain reserved by their retained version history, so creating another project cannot reconnect old private discussions, audit entries, or public responses. Deletion continues to revoke publications and retain historical records according to the existing API contract; a complete legal retention/deletion policy remains pending.

The budget remains a separately selected global ledger because reservations, idempotency, and unsettled holds can span months. Preparation admission and worker claims select global job/control metadata to preserve their current quotas and lease rules. Neither operation loads projects or map baselines.

## Transaction guarantees and limits

PostgreSQL reads use read-only repeatable-read transactions. Writes use serializable transactions and a conservative global advisory write gate, with bounded retries for serialization failures or deadlocks. The gate is acquired before the transaction snapshot. Expensive model/report rendering and external source requests remain outside these callbacks. See PostgreSQL's [isolation semantics](https://www.postgresql.org/docs/17/transaction-iso.html) and [advisory locks](https://www.postgresql.org/docs/17/explicit-locking.html).

The current gate requires direct or session-affine PostgreSQL connections. **Do not put this adapter behind a transaction-mode pooler without adapting and testing the gate.** Short scoped writes address the observed aggregate-copy problem; serialized writes are still a throughput limit. Project/scenario bodies, ACLs, the budget ledger, and some job metadata remain JSON records rather than fully decomposed relational rows. Distributed write concurrency, pagination, retention, and representative production load testing remain open.

SQLite uses a rollback journal, full synchronous durability, explicit read transactions, and immediate write transactions. Connections in the same Node process share an operation queue; SQLite coordinates separate processes. No application callback observes a partially committed multi-record change. SQLite remains a development adapter and is refused in production. See [SQLite isolation](https://www.sqlite.org/isolation.html).

## Migration

Stop all older API instances, workers, and maintenance commands before cutover. Back up the existing data and test migration on a copy first. An older binary must not continue serving its pre-migration snapshot after the new application starts.

For development, `LOCAL_STATE_PATH` still identifies the legacy JSON path, defaulting to `.local/api-state.json`. The new database is `<that path>.sqlite`. On first open, the adapter:

1. Reads the original JSON without modifying it, applies documented defaults for older documents, and rejects invalid/duplicate record identities.
2. Writes normalized records, their original ordinals, deduplicated baselines, and saved content versions inside one SQLite transaction.
3. Reconstructs the complete legacy state and compares its canonical fingerprint before committing the migration marker.
4. Retains the original JSON byte-for-byte. On later opens, a changed legacy checksum causes an error requiring reconciliation instead of silently selecting one writer's data.

A failed migration rolls back. The original file remains available for diagnosis; repair a copy and retry rather than deleting data to make migration pass. Once migration succeeds, new writes go to SQLite. The preserved JSON is **not** a current backup and is never refreshed with new writes.

PostgreSQL migrations run through a separate operator command, never application startup. Entity/security migrations `001` through `020` run under migration/write locks in one transaction. Existing `app_state` is backfilled with matching full-state fingerprints and per-collection counts. The security migration separates password hashes and private moderation details, then reconstructs the full state and verifies its fingerprint again before commit. The original aggregate remains read-only, with triggers rejecting writes from obsolete binaries. Immutable baseline/version tables reject updates, deletes, and truncation. A failed transaction leaves the prior schema/data state intact.

Traffic project format 9 is preserved as complete JSON payloads and immutable revision history. Migration `008` remains the historical fail-closed rule; migrations `009`/`010` add project-owned immutable traffic input and completed-result authority. Every server-run capture in current scenarios, history, undone entries, commands or publications must exactly equal its project-owned immutable artifact and matching completed job. A hash or receipt supplied by the client is insufficient. Explicitly imported captures remain unverified and retain their original numeric evidence; API/core validation still checks integrity, baseline binding and publication rights. SQLite enforces the same completed-artifact comparison for normal full-payload writes. Header-only patches cannot introduce content. Trusted operator migration and backup paths retain original evidence without rewriting its origin. PostgreSQL runtime startup now requires security version 20; caller-set session flags cannot confer migration-owner authority.

Large reviewed traffic requests live in configuration payloads. History/list/idempotency reads use explicit configuration headers; jobs and compact artifact authority do not hydrate native graph, routes, trips or count rows. Reviewed configuration/upload records are append-only. Browser database credentials cannot create them; only the server worker capability with a verified current editor session can admit reviewed inputs. The native worker's full planning payload/baseline access requires an active authorized job, not just a project ID hint.

A single durable [native processing slot](NATIVE_CAPACITY.md) gates traffic, GIS, regional routing and media execution across worker processes. Job claims and slot acquisition are atomic. Hard deadlines do not renew; stale or uncertain work quarantines the slot instead of permitting immediate takeover. Existing running work discovered during an upgrade starts quarantined. Recovery requires trusted operator termination confirmation, an exact token/revision and an audit statement. Budget accounting and fixed-cost opt-in remain unchanged.

Neither migration recreates source data from today's catalog. Missing or corrupt captured baselines cause explicit errors rather than replacement geometry. Orphaned historical records are retained; they are not silently discarded to satisfy new foreign keys.

## PostgreSQL authorization and deployment

Three restricted login roles handle normal requests, account authentication, and preparation/budget/workforce/GIS/traffic/media services. A separate migration owner provisions their grants, policies, and platform-administrator allowlist. Runtime startup rejects superuser/bypass/owner credentials, privileged role membership, schema creation privileges, and incorrect role assignments. The API does not receive migration credentials. PostgreSQL's [row-security rules](https://www.postgresql.org/docs/17/ddl-rowsecurity.html) explain why role separation is necessary in addition to policies.

Normal database authorization resolves the transaction's session hash against an unexpired stored session, user, and workspace membership. User IDs, organization IDs, project selectors, and caller-declared administrator values do not establish identity. Session context is set locally on every transaction attempt and cleared by commit/rollback. Project-only membership does not grant sibling-project access or workspace ownership. Existing workspace owners retain the administration behavior disclosed by the application.

Public snapshot access requires the requested active link ID; it cannot enumerate other unlisted links. Baseline access follows an authorized project or requested public snapshot. Capturing a new baseline requires the complete matching source content, so a guessed private hash cannot attach another team's geometry to a new project. Project versions are archived after authorized writes and remain immutable. Legacy archives use the existing JavaScript canonical-JSON hash; newly archived database rows explicitly identify their PostgreSQL JSON-text hash algorithm. Do not compare hashes across those encodings without reading the stored algorithm.

Passwords live outside ordinary profile rows. Only the authentication connection's exact-email credential lookup reconstructs a password hash; normal roster reads cannot obtain it. Node verifies the password before issuing an authentication-mode session write. Public responders cannot read private moderation reasons; team-authorized reads reconstruct those details separately. Database triggers also protect ACL changes, identity bindings, publication content, comment history, and feedback history. Project-grant removal prunes limited memberships and repairs affected sessions inside the database without returning other users' session secrets to the request callback.

Authentication and worker roles have explicit operation/collection limits. Preparation admission carries the caller's verified session into the actual mutation. Budget workers may reconcile costs and apply the defined overrun pause, while the configured platform administrator controls the ceiling. Startup checks that the application's administrator list matches the operator-managed database list. Changing that list requires the operator migration step; changing the monthly ceiling remains an ordinary authenticated administrator action.

Security migration **18** adds the [cost-review contract](BUDGET.md): append-only reviews and manual ledger corrections, immutable audit history, preserved reservation identity and maximum costs, legal lifecycle transitions, current cost coverage and exact headroom on admission. Preparation workers receive budget read access only. Reviews bind the exact submission snapshot; expired reviews and old months retain unresolved estimates. The SQLite adapter applies corresponding scoped-write guards. This contract was introduced by migration 018 through the operator connection; current runtime startup additionally requires migration 020. Historical migrations remain unchanged.

Security migration **19** adds private media jobs and artifacts, immutable scene/recipe/runtime identities, legal lifecycle transitions, exact project/organization binding, fresh cost-review and fair-use admission, and fenced shared-slot completion. The media worker cannot mutate unrelated services or budgets. Downloads still require current project access. SQLite applies corresponding scoped-write guards. Jobs retain complete source/input archives and frame/output hashes; private content-addressed files live outside the database in the configured media archive. See [MEDIA.md](MEDIA.md).

Security migration **20** adds immutable fiscal-profile versions and idempotent new-study creation receipts. Library reads require full workspace membership; appends require an owner/editor. New studies retain their exact source place and selected proposal, preserving the original project/history and downgrading copied native authority to imported evidence. Profile snapshots and study lineage cannot be replaced on a saved project. Publications must retain the exact publicly permitted fiscal profile. New inline source attestations identify the authenticated submitter and server receipt time. SQLite applies corresponding scoped-write guards. The library retains at most 1,000 versions per organization and 100 per profile family, with cursor pagination over all retained versions. See [fiscal studies](FISCAL.md).

Security migration **7** introduced GIS jobs with creator-only visibility plus current project edit access. The GIS purpose cannot read workforce or preparation records or mutate the budget. Its full project/baseline access uses narrowly granted functions for an active, uncancelled prepare job with a live lease and current creator permissions; the shared worker login has no generic project-payload grant. Prepared imports retain immutable geometry, recipe, provenance and source bytes, with only an initial commit receipt mutable. Database constraints require a completed prepare job and its exact preview to commit together. See [GIS runtime](GIS_RUNTIME.md).

These roles protect individual database connections. The API process remains trusted and holds the authentication/worker credentials; this is not containment of a compromised application process. Already-running repeatable-read transactions may finish using their captured authorization snapshot; subsequent transactions observe logout, expiry, and revoked access. See PostgreSQL's [transaction-local setting semantics](https://www.postgresql.org/docs/17/sql-set.html). Security-definer helpers use fixed trusted search paths and restricted execution grants, following [PostgreSQL's function-security guidance](https://www.postgresql.org/docs/17/sql-createfunction.html).

For a **new dedicated local schema**, follow the commands in [API setup](../apps/api/README.md). `scripts/db-provision.ts` creates three independent random-password logins and a private configuration directory, refusing existing names or files. `runtime.env` contains only runtime connections; `operator.env` contains the operator connection and role names. Files use mode 0600 and the directory 0700. Never install the operator file in the application container. The local Compose password is exclusively a development fixture.

For an **existing schema**, retain its schema/search-path configuration, provision three restricted logins through the database operator, and set `DATABASE_MIGRATION_URL`, `DATABASE_WEB_ROLE`, `DATABASE_AUTH_ROLE`, and `DATABASE_WORKER_ROLE` for the migration command. Supply the matching three runtime URLs separately. The fresh-schema provisioner does not move an existing database or import SQLite data. Rehearse any deployment/cutover on a private copy before switching writers.

## Recovery requirements

A current backup must include the complete normalized database: current rows, immutable baselines, prior project versions, retired-ID protection, credentials, private moderation, security/migration configuration, and audit/history. PostgreSQL recovery also requires the matching roles/grants and separately protected connection credentials. `readPersistedState()` is a trusted QA/export helper for the current application state; its JSON result alone is **not** a full physical backup because it omits archived content versions.

Keep backups private. They contain account password hashes, session material, and private project/response text. They are unrelated to the user-facing public-record export and must not be published under `public/`.

Media recovery requires both the database and the matching private media archive directory. The database backup command does not itself copy external media bundles. Back up that directory separately and verify its retained manifests/hashes before restoring service; a database row alone cannot regenerate missing original export evidence.

The development backup command captures a consistent SQLite image, verifies database integrity and baseline hashes, and writes a new private directory. It includes the matching preserved JSON when migration started from one. It refuses an existing destination and does not implicitly migrate an absent database:

```bash
mkdir -p .local/backups
corepack pnpm exec tsx scripts/storage-backup.ts --source .local/api-state.json --out .local/backups/verified-copy
corepack pnpm exec tsx scripts/storage-backup.ts --verify .local/backups/verified-copy
```

Preserve the whole directory: `state.json.sqlite`, optional `state.json`, and `manifest.json`. For a restore rehearsal, copy it to a separate private directory, verify that copy, then start an isolated development API with `LOCAL_STATE_PATH` pointing to its `state.json` path. A new database created without legacy JSON legitimately has no `state.json` file. Never replace a running database. Automated recovery tests verify current state, archived revisions, retired IDs, checksum failures, private permissions, and safe cleanup of failed backups.

After cutover, rollback requires a verified backup or reconciliation of current normalized data. Starting an older binary against the preserved JSON or `app_state` would lose subsequent changes and can serve stale permissions/publications. Use a separate restore destination, verify the restored application and archived versions, then switch the operator configuration with writers stopped. Production PostgreSQL backup automation, restore drills, RPO/RTO targets, encryption, off-site retention, and deployment rollback remain launch requirements.

## Verification

`storage.test.ts` exercises legacy equivalence and deduplication, zero-geometry metadata reads, scoped deletes/collision rejection, rollback, detached results, immutable revisions, deleted-ID protection, corruption detection, and failed-migration recovery. `postgres-store.test.ts` exercises equivalent database behavior in uniquely named temporary schemas, including multi-connection transactions and an atomic read spanning a concurrent permission/content change. API route tests verify authorization and public-response behavior on the scoped store.

`postgres-security.test.ts` connects as actual restricted logins and executes unfiltered SQL, forged-context requests, privilege-escalation attempts, and cross-tenant writes without application selectors. `postgres-api.test.ts` runs account, save, sharing, review, publication, feedback, revocation, administrator-budget, and preparation workflows through those restricted connections. `gis-security.test.ts` and `gis-postgres.test.ts` cover private conversion admission, isolated worker payload access, exact preview completion, commit, export and revoked access. Their fixtures create and remove uniquely named schemas/roles; they never migrate the development application's schema. Run these with the existing local `TEST_DATABASE_URL` convention. An independent production security review and deployment/load/recovery exercises remain required.

`traffic/postgres.test.ts` verifies actual restricted-role format-9 save, command/history/undo, immutable archive, restart and private/public publication behavior. It also attempts raw SQL traffic-origin forgery in every retained location and publication, including forged owner context. `traffic-storage-guard.test.ts` covers SQLite full-write rollback and unchanged legacy migration evidence. `traffic/storage-security.test.ts` additionally verifies completed-artifact authority, exact numeric binding, immutable reviewed inputs, cross-project isolation and shared-slot claims using actual restricted logins. `traffic/jobs-postgres.test.ts` exercises the complete HTTP path under those restricted roles: exact CSV upload and replay, reviewed input/configuration replay, claim/completion, immutable evidence downloads, adoption, fresh-connection reopen, configuration reuse, cancel/retry, CSRF, viewer/revoked access and tamper rejection. `native-capacity.test.ts` covers multi-connection admission, stale fencing, upgrade/restart quarantine, read-only CLI inspection and explicit recovery. These checks do not establish production capacity or deployment cost compliance.

`apps/api/qa/storage.ts` benchmarks isolated copies of the accumulated development fixture against the previous aggregate algorithm. It records cold migration separately from warm operations, confirms source and final-state fingerprints, and reports scalar timings/loading counters without exposing stored accounts or project text. This is local evidence for the named workload, not a national-capacity or representative-hardware certification.
